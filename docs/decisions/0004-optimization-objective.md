# 0004 自動配置の目的関数

- Date: 2026-08-27
- Accepted: 2026-08-28
- Status: Accepted
- Related specification: Automatic Proposal
- Supersedes: None

## Context

自動提案では、候補コンテナ、配置効率、計算量、手動配置の扱いが競合する。現在の案件Schemaは候補ごとの台数、固定配置、探索設定、提案結果を保存せず、積荷ごとに一つの配置だけを持つ。候補を複数台として同時利用したり、手動配置を固定anchorとして比較したりすると、保存されていない意味を暗黙に追加する。

同じ案件から再現可能な検討案を返し、探索失敗を実積載不能と誤認させず、適用前の案件を確実に保持する契約が必要である。

## Decision

### Proposal Scope and State

- v1は、案件内の全積荷定義をちょうど一度ずつ、一つの登録済み候補コンテナへ配置する完全案を探索する。複数コンテナ同時利用、台数、部分積載、搬出順、固定anchorは扱わない。
- 現在の手動配置は探索入力または固定条件にせず、探索中とpreview中はそのまま保持する。提案は保存・JSON・undo/redoへ含めない派生previewである。
- 提案適用時は、積荷、候補、案件設定を変えず、配置集合だけを完全案へ一括置換する。既存配置がある場合は置換件数を示して確認し、一回の原子的な案件履歴操作とする。Undoは探索前の配置集合を正確に復元する。
- 未保存入力、削除確認、3D drag、永続化処理中は探索と適用を開始しない。探索開始後のProject変更、undo/redo、読込、import、interaction generation変更は結果をstaleとして破棄する。探索中の通常編集は暗黙に失われず、Project変更時に探索だけを中止する。

### Feasibility and Objective

- 完全案は、対象候補へ全積荷を一度ずつ配置し、案件Schemaと意味整合性を満たし、正本の `validatePlacementSet` が計算可能で不適合理由0件でなければならない。
- `opening-path-unverified` と `structure-stability-unverified` を含む未確認理由は提案を拒否せず、previewと適用確認に保持する。提案は実積載の安全性、完全な搬入経路、構造・安定性を保証しない。
- 完全案を得た候補は、内部容積、内部床面積、内部長さ、内部幅、内部高さ、候補IDの昇順で辞書式に比較する。表示名、入力配列順、現在のscene選択を順位へ使わない。
- 一つの候補内では固定ヒューリスティックが最初に得た完全案を採用する。提案はこの固定手順で見つけた最良既知案であり、全配置組合せに対する大域最適性を主張しない。

### Deterministic Search

- 乱数とwall-clock時刻を結果決定に使わない。アルゴリズム版を結果に含め、同じ正規案件、アルゴリズム版、探索上限から同じ結果と理由順を返す。
- 候補は目的関数順、積荷は体積降順、最長辺降順、質量降順、積荷ID昇順で処理する。
- 候補ごとに固定積荷順のdepth-first backtrackingを行う。各深さでは向き、候補点の順に試し、子が完全案またはcutoffなら返し、探索済みなら配置を戻して次を試す。現在の手動配置は探索用Projectへ含めない。
- 許可向きは固定列 `LWH, WLH, LHW, HLW, WHL, HWL` で許可値を抽出し、同じ向き適用後寸法は列内の先頭だけを残す。開口と `dx <= L-2cX`、`dy <= W-2cY`、`dz <= H-cZ` を満たす向きだけを、高さ、床面積、X寸法、Y寸法、固定列位置の昇順で処理する。境界一致を許容する。
- 各DFS深さ・各向きで `X={cX, L-cX-dx, 各配置maxX+cX}`、`Y={cY, W-cY-dy, 各配置maxY+cY}`、`Z={0, 各配置maxZ}` を作る。各軸で座標を丸めずに境界外を除き、正確な整数値で重複排除して昇順化する。その後だけZ、X、Yの三重loopで直積を遅延列挙し、先頭最大2,048点を得た時点で停止する。直積全体または10億点規模の中間配列を生成・sortしない。軸別境界filterと2,048点までの列挙はattemptを消費せず、その後の物理filterはattemptを消費する。浮いた配置を誘発する上側壁Z anchorは作らない。
- 一つの候補につき最大10,000 placement attempt、最大100候補で一要求最大1,000,000 attemptとする。attemptは、一つの積荷、許可向き、候補点の組について、現在のDFS配置と仮配置だけを持つProjectを正本の `validatePlacementSet` で一回評価することとする。評価直前に候補・要求counterをともに1増やし、計算不能または不適合理由があれば次を試す。backtrackと事前filterはattemptを消費しない。
- 1〜10,000回目の候補attemptと1〜1,000,000回目の要求attemptは評価する。上限到達自体はcutoffではなく、未探索の次attemptが存在して10,001回目または1,000,001回目を許可できない時だけcutoffとする。上限ちょうどで完全案を得た場合は成功し、上限ちょうどで探索空間を自然に尽くした場合は探索済みとする。cutoff源はcandidate、request、bothを区別する。
- 候補は目的関数順に探索し、最初の完全案で停止する。先行するより優先度の高い候補がcutoffだった場合は `complete-with-cutoff` とし、選んだ案が目的上最良とは確認できないと表示する。後続の劣後候補は探索しない。
- 完全案を一つ以上得たcutoff結果は、未確認と打切りを表示した上で適用可能とする。完全案がないcutoffは適用不可であり、配置不能を意味しない。
- `no-complete-plan` は、全候補について定義済み探索空間を上限超過なしで尽くして完全案がなかった場合だけ使う。それでも実積載不能の証明とは表示しない。
- Schemaまたは意味検証不適合は `input-invalid`、積荷0件は候補有無によらず `no-cargo`、積荷あり・候補0件は `no-candidates` とし、いずれもattempt 0、previewなし、適用不可、履歴変更なしとする。空の成功案は返さない。

### Worker, Cancellation, and Failure

- 探索は専用のローカルmodule Workerで実行し、DOM、外部通信、同期fallbackを使わない。開始、成功、cutoff、完全案なし、取消、stale、入力不正、Worker失敗を区別する。
- 利用者は探索中いつでも取消できる。取消、Worker失敗、stale、完全案なしではProject、履歴、保存状態を変更しない。
- wall-clock時間は結果を決める打切り条件にしない。合成代表ケースは記録環境で5秒以内、取消要求は250 ms以内にWorker終了へ反映することを初期性能gateとする。対応CPUが未決定のため一般端末へのSLAとは表示しない。
- Worker応答は固定codeと構造検証を使い、案件名、積荷名、入力値をtransport error本文へ反射しない。

### User-facing Meaning

- 成功: 「現行の計算規則を満たす検討案です。完全な搬入経路、構造・安定性、実積載の安全性は確認していません。」
- 未確認あり: 「案には未確認事項があります。適用前に理由を確認してください。」
- より優先される候補が打切り: 「より優先される候補の探索が上限に達したため、この案が目的関数上の最良とは確認できません。配置できる案が存在しないという意味ではありません。」
- 完全案なしの打切り: 「探索上限に達しました。配置できる案が存在しないという意味ではありません。」
- 完全案なし: 「登録済み候補と今回の探索モデルでは、全積荷を配置できる案がありませんでした。実積載不能の証明ではありません。」
- 積荷なし: 「提案する積荷がありません。案件は変更していません。」
- 候補なし: 「提案先の候補コンテナがありません。案件は変更していません。」
- 取消: 「探索を中止しました。案件は変更していません。」
- 失敗: 「計算できなかったため提案していません。案件は変更していません。」
- 適用確認: 「現在の配置を提案で一括置換します。1回の取り消しで元へ戻せます。」

## Rationale

候補を一台ずつ同じ条件で比較すると、現在のSchemaへ台数や固定anchorの意味を追加せず、必要な一候補を説明できる。現在配置を探索中に変更せず、適用を一履歴操作へ分離することで、提案の比較と利用者の手作業を両立できる。

内部容積を第一目的にすると「必要な積載空間」という製品目的を直接説明できる。床面積と各寸法、IDは完全な同点規則であり、安全性や費用を暗黙に保証しない。秒数ではなくattempt数で打ち切ることで、端末性能による提案内容の変化を避ける。

## Alternatives

- 現在配置を固定して未配置積荷だけを追加する: 手作業を保持しやすいが、候補コンテナ比較と全体再配置を妨げ、現在Schemaに固定anchorの意味を暗黙追加するためv1では不採用。後続の「配置を保持して補完」モードとして再検討する。
- 複数コンテナ台数を最小化する: 候補数量と同一型複数台を表せず、現在Schemaの範囲を超えるため不採用。
- wall-clock時間内の最良案を返す: 同じ入力でも端末性能で結果が変わるため不採用。
- 大域最適解を保証する: 計算量と未確定の実務目的に対して過大な保証となるため不採用。

## Impact

- Users: 現在配置を失わず提案を比較し、明示適用と一回のUndoで戻せる。cutoff、完全案なし、未確認、安全非保証を区別する。
- Data: Project、Schema `0.1.0`、JSONを変更しない。提案、探索設定、理由、algorithm versionは派生状態で保存しない。
- Implementation: 純粋な探索、専用Worker protocol/client、preview UI、stale/cancel、原子的適用、履歴actionを追加する。
- Tests: 決定性、目的関数、attempt境界、geometry/validator再確認、Worker状態、preview非変更、適用/undo、WebGL非対応、狭幅、性能を検証する。
- Operations: 外部通信なし。5秒/250 msは記録環境の受入gateであり一般端末SLAではない。

## Compatibility and Migration

案件Schemaと保存値を変更しないため移行不要である。既存案件は現在配置を保持したまま探索でき、適用しない限り変更されない。

## Rollback

仕様、ADR、探索、Worker、UI、履歴、テスト、運用文書を同じ変更単位で戻す。提案は保存されないため案件データの逆移行は不要である。

## Reconsider When

実務試用で固定anchor、複数台、候補費用、重量配分、重心、軸重、積込順、探索上限変更、大域最適性が必要になったとき。
