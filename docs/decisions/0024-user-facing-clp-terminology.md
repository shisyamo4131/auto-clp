# 0024 利用者向けCLP用語

- Date: 2026-08-30
- Status: Accepted
- Related specification: User-facing terminology; Persistence; Automatic Proposal
- Supersedes: None
- Refines: 0004, 0009, 0013, 0023

## Context

Auto CLPの画面と現行文書は、利用者が作成・保存する単位を「案件」と表現してきた。しかしCLPはContainer Loading Planそのものを指すため、「案件」は範囲が曖昧で、保存対象や自動提案結果との関係を理解しにくい。利用者から「案件」ではなく「CLP」とする案が示され、WebGL障害時の退避画面は専門用語より平易な「作業データ」が適切と確認された。

## Decision

- 利用者が作成・編集・保存する正規データ一式を「CLP」と呼ぶ。画面上の名前、設定、入力、保存、履歴、JSON、状態・エラー説明には「案件」を使わない。
- 自動提案が返す未適用結果は「配置案」と呼ぶ。探索内部の完全案や目的関数などの技術用語は、意味を区別する必要がある技術文書・診断で維持できる。
- WebGL障害時の読み取り専用救出画面は、CLPの理解を前提にせず「作業データ」を使う。現在作業と端末保存の違い、固定ファイル名、復旧手順を併記する。
- 内部のTypeScript型 `Project`、`projectId`、JSON Schema `0.1.0`のproperty名、IndexedDB key、固定ファイル名は変更しない。
- 過去のADR、証拠、handoffは当時の記録として書き換えない。現行仕様、運用、受入、ロードマップ、README、UI、テストを新用語へ揃える。
- 利用者が入力するCLP名は自由入力であり、その値に「案件」が含まれても拒否・変換しない。

## Rationale

製品名と操作対象を同じ「CLP」で結ぶと、何を編集・保存・読み込むのかが直接伝わる。「配置案」を使えば、未適用の探索結果と現在のCLPを区別できる。一方、内部識別子や保存契約まで名称変更すると、利用者価値のない広範な移行と互換性リスクを生む。障害時だけ「作業データ」を使うことで、専門用語を知らない利用者にも救出対象を説明できる。

## Alternatives

- 「案件」を維持する案は、CLPとの関係が曖昧なため採用しない。
- すべてを「CLP案」と呼ぶ案は、正規CLPと未適用結果を区別しにくいため採用しない。
- 内部 `Project` とJSON propertyも一括改名する案は、Schema移行と既存データ互換性の負担に対して利用者向け効果がないため採用しない。
- 救出画面も「CLPデータ」に揃える案は、障害時の次行動を平易に伝える目的に合わないため採用しない。

## Impact

- Users: 画面全体でCLP名、CLP設定、CLP保存、現在のCLP、CLPデータ、配置案という一貫した語を使う。保存内容と提案結果の区別が明確になる。
- Data: Schema `0.1.0`、JSONの形・意味、保存済みデータ、固定ファイル名を変更しない。データ移行はない。
- Implementation: 表示文字列と初期表示名を変更する。内部symbol、command、history action id、protocolは変更しない。
- Documentation: 現行仕様を1.0.2へ更新し、現行文書を新用語へ揃える。過去記録は保持する。
- Tests: UI label、status、履歴、永続化、自動提案、物理判定、WebGL gateの文言回帰と通常操作を更新して検証する。

## Compatibility and Migration

保存契約は不変であり、既存JSONと端末保存をそのまま読める。初期表示名だけ「新規CLP」となる。既存データ内の名前や自由入力値は変更しない。

## Rollback

UI文言、現行文書、テスト、仕様版、ADR参照を一括して戻せる。保存データのrollbackや移行は不要である。

## Reconsider When

複数CLP管理、CLP番号、顧客・依頼・運行を別の上位概念として導入する場合、または利用者調査で別の正式名称が承認された場合。
