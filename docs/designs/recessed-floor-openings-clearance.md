# 段落ちと複数開口とクリアランス表示の設計案

- 作成日: 2026-11-04（報告受領日。プレゼン実施日は特定しない）
- 状態: 主要方針は仕様のOpen Decisionsで承認済み。以下の詳細案は承認範囲と区別する。段落ちのコードは実装済み、実機・業務受入は未実施。
- 要望の正本: [仕様のOpen Decisions](../specification.md#open-decisions)
- 作業順序: [ロードマップ](../roadmaps/auto-clp.md#next-work)

段落ちを持つ荷室の再現が採用判断の最初のハードルである。まず床の形状と配置が業務を表せるかを架空ケースで確認し、実間隔と帳票の有用性へ進む。以下のモデル・操作・判定は提案であり、寸法や車種を推測して確定しない。

2026-11-04の判断結果: 長方形一か所の段落ちを採用し、位置・長さ・幅・深さを任意入力する。段差跨ぎは配置確定を拒否する。開口通過判定と積込順は不要。全視点を固定の積荷No付き配置イメージとし、上面図はA4横・1コンテナ1ページとする。採番・エラー時の復帰・表示項目もユーザーが推奨案をすべて採用した。正本は仕様の承認済み次期変更欄で、段落ち先行実装はADR 0046を参照。

## 確認済みの入力と未決事項

2026-11-04のユーザー報告では、段落ちは「コンテナ底面の一部が下がり、より背の高いものを積載できる状態」。位置・深さは不明。背面・左右側面に開口部がある車両も再現したいとの追加要望がある。「クリアランス」は積荷別の要求値設定ではなく、積荷同士・壁面との現在の間隔を表示し、移動中にも追従、PDFにも掲載するものと明確化された。

基本的に上積みをしないため、新規積荷の上面支持可否をFalseへ変更する方針。これは既存UIの「上乗せ禁止ON」に相当し、その積荷自身を別の積荷の上へ置けなくする設定とは異なる。全体の段積み機能の廃止までは要望されていない。

積込計画は最重要機密で外部漏えいを防ぐ必要がある。社外から社内ネットワークへ接続できるのは一定の権限者に限るとの報告。提供形態は未決定で、現行公開技術試用版の本番利用や実データ利用の承認ではない。

## 段落ちの具体案

### 荷室モデル

初回は「平床」または「長方形の段落ち一か所」を採用する。入力は段落ちの開始X/Y・長さ・幅・深さとし、mmで任意に指定する。幅いっぱいの段落ちも一部幅のくぼみも同じ項目で表す。複数の段落ち、傾斜床、L字形は初回の対象外。入力の任意性は、負の寸法や荷室外にはみ出す領域まで有効にする意味ではなく、値域と整合性検証を詳細化する。

座標は従来の通常床をZ=0として維持し、段落ち床をZ=-深さとする案。天井は通常床からの高さHに固定し、段落ち部分の有効高さはH+深さ。例として通常床から天井2,400 mm、架空の深さ300 mmなら有効高さ2,700 mmとなる。これは説明用で実車寸法ではない。床面を低くした分だけ、天井を持ち上げたり他の領域まで容積を増やしたりしない。

段落ちは積荷やダミー箱として登録せず、荷室の構造にする。ダミー箱では重量・積荷数・上乗せ禁止・PDF番号・積込順へ混入するため。既存の最小角アンカーと整数mmを維持し、支持判定を「一律Z=0」から「足元にある床領域の高さ」へ拡張する。

### 配置操作と判定

3Dに床の段差と垂直面を描画し、床領域名・深さを表示する。カーソルが指す床面へ置き、積荷底面全体が一つの床領域に収まれば底面Zをその高さへ合わせる。段落ちの縁を越える移動はプレビューで配置先を示し、確定時のZ変化も明示する。

低い位置の積荷が通常床の構造へ食い込む場合は衝突とする。段差をまたぐ積荷は赤色と「段差をまたいでいます」で示し、配置確定を拒否する。離した時は配置済み積荷を移動前へ、新規配置の積荷を未配置へ戻す。段落ち編集によって既存積荷が跨ぐ場合も編集を拒否し、該当Noを示す。無効プレビューを保存や帳票へ渡さない。架台・渡し板・張り出し支持の例外は設けない。境界接触と跨ぎを区別し、拒否時に座標・向き・配置先・履歴へ中途半端な変更を残さないことを検証する。

側面図に通常床・段落ち床・天井・積荷底面の高さと有効高さを掲載し、上面図だけでは分からない再現性を確認する。重心表示・荷室中心の定義も非直方体化の影響を受けるため、既存の箱の中心をそのまま正しい荷室中心と表示せず、定義を別途確定する。

## 背面と左右側面の開口の具体案

座標案は既存の負X端面を背面として、そこから奥へ+X、背面から奥を見て左へ+Y。左右の呼び方は実務呼称と確認する。開口ごとに安定したID、面、面内開始位置、下端Z、幅、高さを持たせ、三つの開口を一つの荷室へ登録する。下端は通常床基準で、段落ち床に接する開口も表せるようにする。

3Dでは開口を輪郭と名前で表示する案。開口通過の可否判定は不要となったため、開口寸法と積荷寸法を比較する判定や搬入開口の選択を今回の要件に含めない。既存の開口情報を削除するか、形状表示用に保持するかは互換性と併せて詳細化する。

積込順自体が不要となったため、配置イメージ出力を積込順の計算・成功から分離する方針が承認された。現行の直線搬入帯・順序提案を段落ちや三開口へ拡張しない。画面・PDFに積込順番号や順序成立を前提とする説明を残さず、積荷Noとして対応付ける。順序計算の内部資産を残すか削除するかは実装設計で扱う。配置図は実搬入可能性を保証するものではない。

扉の開閉軌跡、柱、取り外せない部材、同時開放の制限は未確認。側面全体が開くとの推測で壁を削除しない。開口面を配置後の境界として扱うか、閉じた扉までの間隔として表示するかも確認する。

## クリアランス表示の具体案

### 測る距離

最初の提案は荷室X/Y軸に沿った表面間距離。選択積荷の前後左右について、その方向を向く面と向かい合う周辺積荷・壁面を対象にする。積荷中心間の距離や、回転前寸法を使わない。X方向なら他のY/Z区間が正の幅で重なる相手を候補とし、正の距離が最小の面を代表表示する。Y方向も同様。対向領域の一部しかふさがない相手がある場合、代表値だけで全面の隙間を説明できないため、詳細表示で同じ方向の相手と距離を一覧できるようにする。

斜めに離れ対向投影がない積荷は「軸方向の対向対象なし」とし、0 mmと表示しない。高低差でZ区間が重ならない積荷を同じ床上の隣接荷と誤認しない。必要なら別機能として斜め最短距離や上方隙間を追加するが、今回の基本X/Y寸法線と混ぜない。段差の垂直面も高さ範囲が対向する時は対象に含める。接触は0 mm、立体重複は距離0として隠さず「重なり」と表示する。

### 画面操作

積荷を選択すると前後左右の代表寸法線と「相手名・方向・mm」を表示し、移動中も同じ配置プレビューから更新する。スナップ後の実際の表示位置を測り、マウス位置の候補座標や移動前の保存座標を測らない。無効な移動が停止した場合は停止後位置の値を表示する。線は対象面間に描き、数値が重なる時は欄外へ引出線を使う。カメラで隠れた線は一覧で読めるようにする。

距離計算は描画から分離した純粋関数とし、画面とPDFで共通利用する。距離は配置から再計算し、保存項目にしない。選択荷に絞ることで常時全組合せ表示を避け、移動終了・取消・Undo/Redo・回転・コンテナ切替で古い距離を残さない。性能は対応端末と代表件数で測定し、未測定の応答時間を約束しない。

既存の必要最小間隔と今回の実間隔は別概念。最小値の設定・合否を残すかは未決であり、表示追加に伴って既存JSONの隙間設定を無効化しない。0 mmへのスナップと必要最小値違反が共存する場合も、実距離と判定理由をそれぞれ表示する。

### PDF

全視点を積荷No付き配置イメージとして出力し、積込順の計算を出力条件にしない。上面図は天井を非表示にした真上からの平行投影、A4横・1コンテナ1ページとし、長手方向を紙面横へ向ける。ページにはCLP名・コンテナ名・出力日時、前後左右、荷室内寸の長さ・幅、積荷外形・No、段落ちの破線境界・位置・長さ・幅・深さ、配置イメージの表記と単位mmを載せる。段落ち境界は積荷で隠れても追える表示にする。名称・重量は別ページの一覧へ分離する。縮尺は自動調整し、A4で読めなければ文字の縮小を続けずA3等を後続検討する。

NoはCLP全体で登録順に1から自動採番し、画面・全視点・一覧で一致させる。移動・回転・コンテナ変更・保存・再読込・再出力で維持し、削除番号は再利用しない。顧客側管理番号は別欄とする。CSV全件置換では新規の積荷として採番し直す。旧データへの番号付与、Undo/Redo、採番状態の保存、CSV置換時の番号範囲の扱いは、この識別性を守るデータ契約として具体化する。

出力開始時の配置を固定し、図・一覧・距離を同じ状態から生成する。上面図に積荷番号と間隔線を置き、同じ積荷ペアの重複線をまとめる。別表に「積荷番号／相手番号または壁面・開口名／方向／距離mm」を載せ、図の文字が密集した場合は図を分割する。代表距離だけの図と、全対象の明細を区別し、省略した対象がないよう一覧との対応を検証する。「全対象」は対向面ルールで定義し、無関係な全積荷ペアの距離を大量に列挙しない。

段落ち領域の境界・深さと開口IDを図に記し、高低差は側面図で補う。測定対象と方向、搬入経路未確認の範囲を注記する。用紙、縮尺、許容文字密度、全壁までの寸法を常に併記するかは先方と確認する。

## 機密性と提供形態の検討案

ブラウザを使うこと、インターネットから配信すること、計画データをサーバー保存することは個別に決める。現行は静的クライアント・端末内保存であるが、その設計だけで漏えい防止の確認が済んだとはしない。根拠は[ADR 0001](../decisions/0001-local-first-web-architecture.md)と[ADR 0038](../decisions/0038-github-pages-technical-preview-and-future-hosting.md)。

| 候補 | 提案するデータの扱い | 導入前の確認 |
| --- | --- | --- |
| 社内限定Web配信 | 社内でアプリを配信し計算は端末内、外部へ計画を送らない | 社内配信担当、認証、管理端末、保存先、更新手順、外部通信遮断下の動作 |
| 端末へ配布して実行 | アプリ・必要資材を端末内へ配布、計算・保存も端末内 | 配布・インストール権限、実行方式、オフライン起動、バックアップ、更新・版管理 |
| インターネット公開配信 | 現行技術試用方式を候補として再評価 | 外部からコードを取得することの可否、通信先・更新コードの管理を含む先方の許容条件 |

まず社内限定配信と端末内実行を先方管理担当者と比較する案。方式は未採用で、具体的な配布製品・ライブラリは選定していない。外部CDN、フォント取得、解析・障害送信、更新、ライセンス確認、サポート経由を含む通信の有無と送信内容を検査する。PDF/JSON、印刷、ブラウザ保存、OSの同期フォルダ・バックアップ、共有端末、権限・保管・削除も対象にする。架空データで通信観測・遮断・再起動・保存復元を検証し、先方の管理条件と照合してから実務導入を判断する。漏えいゼロを未検証のまま保証しない。

## 互換性と実装承認の境界

既存JSONは平床・単一開口のまま読める方針とする。段落ち・複数開口を保存する場合は新しいデータ契約と明示的な移行が必要で、現行Schemaに未知項目を混ぜない。旧データを新モデルへ移す時は、旧原点・配置・重量・上乗せ禁止・隙間値を保つ。新形式を旧版へ戻す場合、段落ちや開口を黙って削除せず変換不可を通知する。導入前の原本を保存し、新形式対応前の版へ戻しても原本を開ける退避方法を検証する。

初期値変更は新規作成だけに適用し、既存JSON・端末保存にあるTrueをFalseへ書き換えない案。複製がある場合の継承規則も実装調査で確認する。間隔表示だけなら派生情報なので保存形式を増やさない。

採用する詳細案が決まった時点で、仕様・ADR・データ契約・受入・運用・ロードマップ配点・実装・テストを整合させる。本作業は要望記録と設計までで、現行ADRをAcceptedのまま新意味へ書き換えない。段落ち先行実装の保存契約・ロールバックは[ADR 0046](../decisions/0046-recessed-floor-and-save-compatibility.md)へ確定した。配信設定は変更しない。

2026-11-04具体化。以下は段階計画。P1床計算とP3段落ち操作、P2の保存・固定No基盤を実装した。上乗せ禁止初期値、全CLPの順序廃止、P4/P5は残作業。採用済みの製品要件は仕様を正とし、保存項目名・新しい形式版・端末保存キーは実装時の契約で確定する。実在の輸送情報を使わず架空データで進める。最初の到達点は「段落ちを設定し、背高荷を配置し、保存・再読込で同じ配置を復元できる」。複数開口、間隔表示、配信方式の決定を待たない。ただし実務データでの導入は機密性の確認を別途必要とする。

| P4 配置イメージPDF | 順序非依存snapshot、全視点のNo、一覧、A4横上面図専用ページ | PDF系が合格し、同一snapshotの全図・一覧・Noが一致。上面図を人間が判読できる。暫定帳票停止を解除 |
| P5 採用判断の試用 | G1と上面図をユーザーが確認し、先方へ提示する架空ケースを確定 | 段落ちの再現・編集・復元と、上面図による説明の可否を個別に記録。機能が動くことと業務有用性の判断を混同しない |

G1（最優先の到達点）はP3完了時に提示する。P4完了を待って段落ちの確認を遅らせない。クリアランス表示・三面開口・社内配布は後続。日数・達成率は未見積りで、既存試作99%を今回の達成率に流用しない。

### 保存互換性の実装案

現行Schemaは `0.1.0` 固定で未知項目を拒否し、serializerは項目を明示列挙する。追加フィールドをUIだけに持たせると再読込で失われるため、新しい形式版を導入する。版番号はP0で確定し、同じ版の意味を変更しない。

- 新しい保存情報: 荷室ごとの平床／長方形段落ちの区別と位置・長さ・幅・深さ、積荷ごとの固定No・顧客管理番号、採番済み最大値を保持する。Noは内部cargo IDの代わりに参照キーとして使わない。画面色・距離・床判定・画像・PDFは保存せず再計算する。
- 旧JSON: まず旧Schemaと旧意味規則で検証し、成功したものだけ新モデルへ非破壊変換。床は平床、Noは保存されている積荷配列順に付与する。旧データには登録順履歴がないので、当時の登録順を復元できたとは表示しない。既存ID・座標・向き・重量・支持設定・隙間・開口情報は保持し、既存の向き正規化経路とも整合させる。
- 新JSON: 新Schema・参照・番号重複・採番状態・床領域を検証。位置は非負、長さ・幅・深さは正の整数mm、段落ちは荷室平面内に収まることを条件とする。数値上限と深さを含む加算・座標範囲は現行値域を調査してP0で確定し、丸めや勝手な切詰めをしない。
- 無効な段差跨ぎを含む新JSONは、読込確定前に拒否して現CLPを保持する案。元データを修正せず理由と対象Noを通知する。平床の旧JSONにある修正途中配置を、新しい段差跨ぎ規則と混同して拒否しない。構造・参照の不正と既存の物理的不適合は区別する。
- 読込手順: サイズ・構文・形式版・形式別Schema・参照検証→必要な移行→新形式検証→床・配置評価→一回の状態置換。どの失敗でも現在のCLP・履歴・選択状態・端末保存を変更しない。読込だけで移行済み内容を端末へ自動保存しない。
- 端末保存: 旧保存枠を上書きせず、新形式専用の保存先を用意する案。新枠がない場合だけ旧枠の移行読込を提供し、新枠破損時に古い内容を黙って復元しない。新枠の保存は一取引で行い、失敗時は以前の新枠と旧枠を保持。削除は対象の保存枠を明示し、退避した旧枠まで連動削除しない。具体的なキー・DB版はP0で定義する。
- 旧版へ戻す場合: 旧原本JSONまたは残した旧端末枠から復旧。新形式は旧版で非対応として拒否させる。段落ち・No・顧客番号を黙って消す旧形式書出しは初回に提供しない。新形式で行った編集が旧原本に含まれないことを案内する。

採番の技術案は、削除後も最大値を保持し、新規に最大値+1を使う。CSV全件置換は旧積荷の続きの未使用番号を行順に付与して、過去の図面と番号を衝突させない。失敗した追加・CSV処理は番号を消費しない。同一編集のUndo/Redoでは対象積荷のNoを復元する。Undo後の新しい分岐でも一度採番済みの番号を別の積荷へ再利用しないよう、採番済み最大値を単純なProject巻戻しと分離して管理・保存する。この案は顧客との識別を優先する実装方針で、旧形式の復旧原本へ番号履歴を後付けしない。

### 代表ケースと検証項目

G1は架空の荷室6,000×2,400 mm、通常床から天井2,400 mm、段落ちをX=2,000・Y=400・長さ2,000・幅1,600・深さ300 mmとする。隙間設定はこの幾何試験では0 mm。1,000×1,000×2,600 mmの積荷を段落ち内のX=2,500・Y=700・Z=−300へ置くと上端は2,300 mmで天井内、通常床なら上端2,600 mmで天井超過となる。これは計算用合成例で実車仕様ではない。

| ID | 検証項目 | 期待結果 |
| --- | --- | --- |
| F1 | G1と平床比較 | 低床内では床接触・天井内。通常床では高さ超過。負Zだけを理由に低床配置を不適合としない |
| F2 | 縁ぴったり／1 mm跨ぎ、幅いっぱいの段落ち | 接触と跨ぎを区別。跨ぎをエラー、幅いっぱいでも内外判定が成立 |
| F3 | 深さ0・負値・小数、領域外、上限、算術境界 | 無効入力を原子的に拒否。正の深さの床下1 mm、天井の等値／1 mm超過も独立判定 |
| F4 | 通常床から低床、低床から通常床、支持荷・旧床下診断 | 足元に応じたZ。積荷支持・床衝突を混同せず、低床を0へ補正しない。床との接触はZ隙間の例外を維持 |
| E1 | drag・座標編集・回転・積荷寸法編集で跨ぐ | すべての確定入口で拒否。同じ形状なら入口によって結果が変わらない |
| E2 | 床位置・深さ・寸法変更／段落ち削除で既存配置を無効化 | 該当No表示、変更前の床・全積荷を保持。自動で荷を動かさない。高さだけ変えた場合の支持喪失も確認 |
| E3 | drop・Escape取消・競合・Undo/Redo | 移動前／未配置へ戻り、無効状態・履歴・番号変更を残さない。合法な編集だけ一回のUndo/Redo |
| S1 | 旧平床JSON・旧端末保存の移行 | 旧原本不変、配置・設定維持、決定的No。旧形式の負座標修正途中データも意図なく書換えない |
| S2 | 新形式のJSON・端末保存往復 | 段落ちと配置・No・顧客番号・採番済み最大値が一致。保存値から3D・物理結果を再構築 |
| S3 | 不正形式版・未知項目・破損・参照不整合・容量超過・DB失敗 | 現CLPと旧原本を保持。読込成功まで画面を置換せず、新保存失敗で旧枠を消さない |
| S4 | 旧アプリで新形式を開く／新版から旧原本で復旧 | 非対応として拒否、平床への誤変換なし。旧版で旧原本が復元できる |
| N1 | 削除・追加・コンテナ移動・履歴分岐・CSV全件置換 | Noの固定・欠番非再利用・原子的採番。全置換時も旧Noと混同しない |
| P1 | 上面図と全視点・一覧 | A4横上面図専用ページ、No対応、前後左右、単位・内寸・境界・深さ・日時。長名・密集・白黒印刷でも判読確認 |
| P2 | 旧順序では循環／開口に収まらない配置 | 新しい配置図は順序・開口判定に依存せず出力。順序番号や古い開口不適合理由が残らない |
| P3 | 出力途中の編集・取消・フォント／画像生成失敗 | 同一snapshotを維持、不完全PDFを成功扱いしない、未確定プレビューは含めない |

床の非直方体化は幾何中心表示にも影響する。段落ち対応時の荷室中心は通常箱の中心と誤認させず、定義の再検討または理由付き表示停止をP0で選び、G1に古い値を残さない。積荷重心自体は負Z座標でも計算を回帰する。荷室外の仮置きZ=0は低床と別の作業面として維持する。

### 検証の実行と文書の切替

実装変更は `application-logic`、`data-contract-schema-migration`、`ui-css-layout` の影響範囲に分類し、[検証policy](../../governance/verification-policy.json)と[運用matrix](../operations.md)の和集合を使う。反復中は変更した純粋関数・保存・commandの対象試験を先に実行し、UI接続後に対象browser試験、段階の完成時に該当completion gateを最終状態に対して実行する。G1とPDF完成を混同しない。

保存形式を含む段階の完了ゲートは `git diff --check`、`corepack pnpm run typecheck`、`corepack pnpm run lint`、`corepack pnpm run test:unit`、`corepack pnpm run test:browser`、`corepack pnpm run build`、`pwsh -NoProfile -File scripts/check-data-contract.ps1`、`pwsh -NoProfile -File scripts/check-governance.ps1`、`pwsh -NoProfile -File scripts/check-project.ps1`。各コマンドの結果・終了コードを個別記録し、包含されるrendererとproject-governance-regressionは重複実行しない。ここに挙げた実装試験は計画であり、まだ実行・合格していない。

P0〜各実装段階で仕様・関連ADRと索引・データ契約・受入・運用・変更履歴を影響範囲だけ更新する。保存先変更の案内と復旧手順を運用に追加する。現行仕様の開口判定・積込順に関する記述を残したまま、新版完成とはしない。外部公開・実データ利用・本番移行はこの計画の実行に含めない。
